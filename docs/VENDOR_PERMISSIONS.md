# Central vendor permissions
Existing Users, Role, PageMaster and RolePermission are authoritative; VendorUsers remains the store membership boundary. Vendor page codes are stable, legacy admin page IDs and grants are preserved. Vendor role grants apply across explicitly assigned stores. Finance remains owner-only. Stock requires listing view as its navigation entry. No vendor grants are seeded in production: the super admin must explicitly configure them. Missing rights deny access. No new admin roles or admin policy changes are introduced in this batch.

Deployment order (restored database only): confirm legacy PageMaster/RolePermission column names, types, constraints, identity and duplicates; apply 14-vendor-permissions.sql after role seed; reapply inventory/04-post-adjustment.sql and marketplace/08-vendor-fulfillment.sql; deploy application; configure intended role grants; run SQL and HTTP/browser regression tests. Keep vendor flags disabled on production until acceptance. The application requires the permission migration before deployment. Do not silently remove duplicates or cross-scope grants. The script is repeatable and does not grant access. Existing role names are still the portal classification boundary; do not rename reserved vendor roles.

Admin controllers currently use existing Admin/SuperAdminOnly policies. Full admin dynamic permission enforcement, stable admin page mapping, migration from email-based super-admin identity, and real HTTP/browser testing are separate acceptance gates; do not treat this batch as production certification.
