# Staff authentication hardening
Scope: dbo.Users staff only; Customers have separate credential writers and are not migrated here. External vendor login remains disabled. The old admin policy still uses its existing email restriction; replace with a verified permission migration before vendor activation.

Deployment is not approved by build alone. Run scripts/security/01-staff-password-preflight.sql against restored production data. Confirm column capacity, duplicate emails, and that no plaintext begins with the reserved staff-v1: marker. Review all external integrations before deploying; the previously unauthenticated UserApi writes now return 405 to authorized callers. Use existing admin user forms. RoleApi now requires super-admin and antiforgery for writes. Back up securely and invalidate old admin sessions at release. Rotate potentially exposed credentials; assess logs for unauthorized access. Do not deploy old binaries after hashing starts.

New/changed staff passwords use salted ASP.NET Identity hashes, minimum 12 characters. Existing plaintext is rejected by default. For migration only, explicitly set Authentication__AllowLegacyStaffPasswords=true in the protected test/release environment; verified legacy login upgrades that row before signing in. Disable the flag after all remaining staff reset/migrate. Legacy passwords are case-sensitive now. Never re-enable legacy fallback as a long-term option. No hash or plaintext is included in staff list response/edit models. Production migration and reset workflow remain unverified. Customer passwords and customer API authorization need a separate remediation.

CI tests password helper only; pending integration tests: unauthorized API requests, cookie invalidation on inactive account/role, CSRF, login upgrade and retry, password change, blank edit, admin role and duplicate email handling, production schema and browser flows. Existing cookies are checked for active admin identity each request, not yet invalidated by password changes. Do not invite vendors.
