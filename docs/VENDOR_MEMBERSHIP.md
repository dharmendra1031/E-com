# Vendor membership — phase 4A
Apply 01-create-schema.sql and 02-seed-vendor-roles.sql on restored test database first. Existing Role table and Users remain authoritative. Seed creates role names only; no user, permission or login grants. Existing role rows are not overwritten or reactivated. Review any pre-existing roles and assignments before activation. Use existing Users screen to create vendor-role staff; use Vendors > Users to assign/revoke membership. Users may be assigned to more than one vendor explicitly; the same role applies to their memberships in this version. Vendor membership uses composite primary key; never delete historical membership. Existing SuperAdminOnly and VendorMasterEnabled gate applies to every action; existing hardcoded admin policy is not yet replaced. New vendor sign-in remains blocked by AccountController. Pending vendors may be prepared, suspended vendors cannot receive/reactivate memberships. Actual future vendor access must require approved vendor, active membership, active account, current vendor role and page permission on every operation; never trust a posted VendorId alone.
SQL fixture verifies role seed repeatability, duplicate membership, independent revocation; it does not prove HTTP authorization or vendor runtime isolation. Pending: actual database, CI, browser/CSRF, concurrent membership creation, unauthorized admin endpoints, customer security, credential migration and role permission enforcement. Do not enable vendor sign-in. Do not deploy to production before previous auth migration prerequisites and security tests.
