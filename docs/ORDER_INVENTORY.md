# Order inventory lifecycle — phase 8A
Apply 05-order-reservations.sql after the listing inventory migration and adjustment procedure. Only internal trusted order service may execute these procedures; do not expose via public API or grant direct execution to vendors. No application callers enabled yet. Before integration restrict database grants, persist immutable server-validated listing/quantity/price snapshots per order and compare reservation input to them; never use client-supplied listing quantities directly. The procedure requires existing order and approved vendor, listing and active product. One aggregated row per listing, maximum 100 distinct listings per order (chosen initial bound, review before launch); expiry up to 24 hours (technical bound, not a payment timeout policy). Identical reservation retry requires same expiry and quantities, still Reserved. Finalized reservation cannot reopen; use new order or explicit future recovery. SQL order lock serializes lifecycle for same order; balance conditional updates protect availability; ascending listing order minimizes deadlocks, but concurrent stress tests and retry handling remain necessary. Multi-item basket is atomic. Procedures support outer application transactions; SQL errors roll back the entire transaction, so callers must abandon failed transaction and restart from verified state. Do not hold database transactions across payment gateway calls.
FinalizeOrderInventory consumes for verified payment; releases for conclusively verified payment failure, unpaid cancellation or verified expiry. The caller MUST validate MyFatoorah server-to-server status and order linkage before calling. SQL reason is a trusted caller assertion, not proof of payment. Expiry only checks deadline; no background release job. Late payment after release must enter reconciliation/refund workflow, never consume released stock. Repeated same terminal outcome is idempotent; different outcome rejected. Existing approved reservations can finalize after vendor/listing suspension. Paid cancellation/physical return restocking needs an approved return-item ledger with quantity ceilings and duplicate event keys; not implemented in this phase. Legacy checkout and stock are unchanged. Tests exercise actual procedures in disposable SQL DB, not real concurrent checkout or payment verification.
