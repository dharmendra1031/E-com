# Vendor portal — phase 5A
The existing default cookie remains unchanged for admin/customer. VendorPortal is an explicit, separate scheme, cookie name and path, and policy. Vendor accounts still use dbo.Users with staff-v1 hashes; no plaintext fallback or duplicate user table. Vendor portal is OFF by default; enable Marketplace__VendorMasterEnabled=true and Marketplace__VendorPortalEnabled=true ONLY on restored test environment after earlier migration checks. Do not enable on production.
Portal /vendor-portal/login uses antiforgery, HTTPS-only nonpersistent cookie, 3h expiration and per-IP fixed-window limit (10/minute per app instance). Behind proxy configure trusted forwarding and distributed/account-based throttling before external use. Login requires approved active membership, active user/role and a vendor role. Cookie validation rechecks role/email/credential fingerprint and at least one approved active membership each authenticated portal request. Each store query scopes to UserId + VendorId + approval and membership; unknown/unassigned stores return 404. Vendor login does not issue a default cookie. Logout affects vendor cookie only. Dashboard deliberately shows real store identity only; sales/stock/financial KPIs not wired. No vendor product/order endpoints or permission grants yet.
Tests in existing StaffPasswordChecks cover role, identity scheme, cookie configuration, credential version. They are not full HTTP isolation or database tests. Pending: HTTP/browser tests (vendor cookie alone cannot authenticate admin/customer routes, default cookie cannot open vendor portal, cross-vendor direct URLs, revoked memberships/role/password, CSRF, rate limiter, logout), real SQL query integration, audit of existing anonymous/weakly protected endpoints, page permissions, customer authentication, superadmin permission migration. Separate cookies do not repair existing unauthenticated legacy APIs. Do not invite external vendors until those gates pass.

## Integrated seller workspace
Existing permissions remain mandatory. Products and Inventory are separate navigation entries; inventory requires both vendor.listings and vendor.stock and VendorInventoryEnabled. The Admin and vendor stock registers share the same paged balance query; vendor always supplies its authorized vendor ID. Returns is read-only, requires vendor.orders plus VendorOrdersEnabled and ReturnWorkflowEnabled, and omits customer identity and free-text reasons. Packing/delivery remain in Orders; commission and test settlement share FinanceReview (owner only). Dashboard uses verified paid suborder counts and five recent orders, not fabricated sales or payable figures. No automatic permission grants, new database tables, production flags, or financial policy changes. Apply existing marketplace migrations (including VerifiedMarketplacePaidOrders) before testing. Local config and role mappings must be checked independently; source changes do not enable local deployment. Browser and direct URL isolation tests remain acceptance gates.
