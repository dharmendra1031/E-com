# Marketplace order attachment — phase 11A
Apply 04-vendor-orders.sql and 05-attach-marketplace-order.sql after earlier marketplace/cart/inventory migrations on a restored database. Schema must be applied before updated EF binaries even with features off. Existing Orders and OrderItems reused; VendorOrders is one suborder per vendor per parent. Product names, seller SKU, vendor name, quantities and unit prices are snapshots. Suborder subtotal is merchandise only; tax, delivery and payment are parent-level until allocation rules approved. No coupon support. No new status codes; internal procedure expects existing pending/unpaid (1/2) parent, confirm actual status master in restored DB. Trusted service must create parent with unique customer/request ID, validated customer/address, server-calculated approved charges and expected quote in outer transaction, invoke AttachMarketplaceOrder, then commit. Procedure checks full seller cart, current approved listing prices and total, snapshots and reserves all listings via existing ReserveOrderInventory, removes only seller lines. Any error rolls back entire outer transaction. On retry caller looks up customer/request ID and checks immutable quote/address before reporting success; do not call attachment twice. No public caller, no payment record, no gateway call, no paid claim. SQL fixture tests split, totals, rollback, changed price, insufficient stock and legacy cart preservation. EF global filters isolate staged orders and lines from legacy EF queries; raw SQL, RDLC, mobile, gateway, admin and older binary paths still require audit, and no live orders may be written before then. Filtered-index session options and migration compatibility need restored DB tests. Delivery, VAT, commission, refund allocation and status transitions remain pending approval; no business rule for these invented. Do not expose or grant public execution. No production activation.

## Phase 11B — isolated development checkout
Use only an isolated restored/disposable SQL database. Requires ASPNETCORE_ENVIRONMENT=Development and Marketplace__CustomerOfferPreviewEnabled=true, Marketplace__SellerCartEnabled=true, Marketplace__SellerCheckoutTestEnabled=true; production/staging environments return 404 regardless of flags. Shared cart reader and customer authorization are reused. Quote is data-protected, bound to customer and request ID, expires after 10 minutes for new orders. On POST recheck customer, owned valid area/block address, saved quantities/prices, current seller eligibility and stock, existing CompanyDetails delivery/VAT settings (test assumption only). No coupons; parent charges once per order for testing, not approved marketplace tax or delivery policy. Reserve for 15 minutes in the same serializable transaction as pending order and SQL attachment. No gateway or Payments row written; no paid or fulfillment action. Same signed request returns existing order only if address, totals and immutable lines match. Recovery uses same POST or owner-scoped receipt request ID, even after quote expiry while key remains valid. Do not hold real stock; automatic release/expiry worker, payment and late-payment handling are NOT integrated, so test reservations require isolated DB cleanup/reconciliation. Existing legacy checkout remains separate. Address ID verified, immutable address snapshot pending. Test coverage for quote arithmetic, tampering, ownership and changed quantities; actual HTTP, concurrency, exception recovery, database grants, data-protection key persistence and browser validation remain pending. No live rollout.
