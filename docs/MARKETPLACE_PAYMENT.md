## Sandbox payment recovery
A Starting attempt with a lost invoice link can now be recovered from the owner-scoped receipt. The return GET only displays an optional payment reference; an antiforgery-protected POST queries existing GetPaymentStatus with KeyType=PaymentId. The successful transaction must match that ID, the exact stored merchant reference, invoice value, currency and paid status before the existing Link/Confirm procedures are called. Linked attempts continue to verify by stored invoice ID. Retry never calls SendPayment. Gateway failures remain pending and the receipt displays a bilingual review message. Both payment POST actions are rate limited per IP in the current instance. No automatic release of uncertain invoices. Actual sandbox gateway, callback and lost-response HTTP tests and production webhook/reconciliation work remain required. This is not a live enablement or a replacement for mobile checkout.

## Safe expiry and operator reconciliation
Reapply 06-marketplace-payment.sql on the isolated development DB before testing. Marketplace__ReservationExpiryWorkerEnabled defaults false; it registers the worker only in the existing Development checkout gate. The one-minute scan processes up to 50 candidates; SQL rechecks expiry, order status and absence of attempts/payments under the order lock shared with payment initiation. A started or linked invoice must never be released by the worker. Stock release is idempotent and does not alter commercial order status. The SuperAdmin-only payment review has a sandbox-only POST to reconcile a previously linked invoice via the same gateway verification and SQL posting as the customer receipt. The action uses the stored invoice, never a client-provided amount or status. No automatic gateway polling or webhook in this batch. A Starting attempt still requires customer reference recovery or manual investigation. Test in an isolated database; no production rollout or real gateway request performed.

## Automatic linked-invoice reconciliation
Apply the updated 06-marketplace-payment.sql to the isolated development database. Marketplace__PaymentReconciliationWorkerEnabled defaults false; the existing single maintenance worker handles both expiry and reconciliation, gated by Development, checkout flags and the exact sandbox endpoint. It selects up to ten linked unpaid orders per scan (at least one minute after linkage), using the persisted expected amount and merchant reference. Each candidate reuses VerifyLinkedAsync and ConfirmMarketplacePayment. It does not initiate payments, treat failed lookups as terminal failures or release started reservations. Cursor rotation avoids blocking all later orders behind old pending invoices. The database posting procedure remains the concurrency/idempotency boundary if customer/admin/worker verification overlaps. Multiple app instances may duplicate read-only gateway lookups; deploy one enabled worker in sandbox. Existing gateway HTTP client has its own timeout and does not yet accept cancellation; slow calls may extend a scan and delay the next expiry pass. Signed webhook, retry scheduling for scale, actual gateway and worker integration tests, terminal nonpayment handling, and production activation remain pending. No live transaction or schema deployment performed.

## Signed MyFatoorah webhook V2 (payment status only)
Official references: https://docs.myfatoorah.com/docs/webhook-v2-payment-status-data-model and https://docs.myfatoorah.com/docs/webhook-signature.
Configure HTTPS POST /api/marketplace/myfatoorah/webhook in the sandbox portal, select only PAYMENT_STATUS_CHANGED, version 2, and configure retries. Marketplace__SignedWebhookEnabled defaults false; supply Marketplace__WebhookSecret using a deployment secret store, never source code. Existing Development/sandbox flags remain mandatory. The endpoint requires the MyFatoorah signature, exact V2 event type, canonical signed fields in the documented order, HMAC-SHA256/base64 and constant-time comparison. It accepts only the documented string field format (null external identifier becomes empty), rejects duplicate signed fields, and limits body size to 64 KiB and requests to 60 per minute per app instance. Non-paid signed events do not change stock or payment. Paid events independently query GetPaymentStatus by PaymentId, match gateway invoice, exact merchant reference, currency, transaction amount and persisted attempt, then reuse the existing Link/Confirm procedures. Repeated paid events use SQL idempotency; a concurrent link race may return 503 and succeed on a later retry. Unmatched or inconclusive paid events return 503 for review/retry; no arbitrary order or amount is trusted from the webhook. No gateway POST or new invoice is initiated. No raw webhook payload is stored. The worker remains the fallback for linked invoices. Unit checks include a fixed independent HMAC vector. Live HTTP delivery, real sandbox signature payload compatibility, concurrent delivery and multi-instance throttling remain acceptance gates. Refund/dispute events are not handled. No portal configuration or live payment performed.
