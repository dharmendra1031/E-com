# Marketplace finance preview
Install 11-vendor-finance.sql after return workflow. Marketplace__FinancePreviewEnabled defaults false. Explicit vendor rate, versioned append-only policy (no seeded default); 0% only if deliberately saved. Superadmin application policy plus active Admin database actor; stale policy updates rejected. During original development checkout, snapshot all vendor rates and rounded commission on merchandise subtotal only, excluding VAT/delivery. Missing policy rolls back complete order; legacy/test orders created before enabling stay unsnapshotted and are not backfilled. Calculation basis and three-decimal rounding are proposed test rules, not approved commercial terms. Finance review only shows paid suborder merchandise and commission; return history flags financial review. Not a settlement balance, liability posting, payout approval, or refund. No actual funds transferred. Need approved commission basis (category overrides etc.), VAT/fees/shipping allocation, refund/reversal policy, settlement cycle and gateway supplier capabilities, immutable accounting journal/payout evidence, concurrency and browser acceptance before activation. Test verifies missing policy rollback, actor, historical snapshot and stale change.
## Return-aware finance reconciliation
Reapply 07-return-receipts.sql, 10-marketplace-returns.sql, then 11-vendor-finance.sql before deploying the updated application. The existing return receipt transaction now records the authenticated reviewing actor in InventoryTransactions.CreatedBy for new workflow receipts; historical rows are not modified. Review rechecks paid gateway attempt, and Admin receipt confirmation requires explicit human inspection attestation at the HTTP endpoint. The finance view aggregates physical receipts and pending/approved requests separately per vendor suborder. Remaining merchandise equals original merchandise less physical receipt value; pending/rejected returns do not reduce it. Original rate and commission are unchanged. Both Admin and vendor owner review screens use these same amounts. No refund, commission reversal, approved balance or payout is inferred from these amounts. Commercial policy, damages, shipping/VAT/fees, provider refunds and settlement journal are still required before funds can move. SQL fixtures verify receipt actor, partial vendor isolation, pending/rejected distinction and original commission. No new tables or dependencies.

## Sandbox refund attempts
Apply 15-refund-attempts.sql after 12-refund-review.sql before updated application. One durable row per physical return holds explicit operator-approved test amount, original invoice, unique external identifier and verified gateway refund ID. SandboxRefundEnabled defaults false and requires the existing development-only MyFatoorah test checkout configuration plus FinancePreviewEnabled. Superadmin only. The amount is limited to merchandise receipt and total invoice, including uncertain attempts. Existing unrecognized gateway refunds block new submission. V2 MakeRefund uses the same external and idempotency key; there is no automatic retry. GetRefundStatus by original invoice independently verifies exact reference, invoice, final Refunded status, requested and actual amount, and KWD. Missing/canceled/pending or mismatched responses remain unresolved, not paid or retried. No original payment, stock, commission or vendor payable is modified. No supplier deduction is sent; service charge on customer false is a sandbox-only assumption. The single attempt per return and external refund block intentionally require manual support if uncertain or canceled. Production refund policy, external gateway concurrency, actual sandbox acceptance, signed refund webhook and settlement journal/payout remain pending. Source: https://docs.myfatoorah.com/docs/make-refund ; https://docs.myfatoorah.com/docs/getrefundstatus ; https://docs.myfatoorah.com/docs/idempotency .

Only one unresolved attempt per invoice is allowed by SQL under the parent order lock, including across multiple return lines. A failed or inconclusive inquiry never authorizes another request.

## Sandbox settlement ledger
Apply 16-settlement-ledger.sql after 15-refund-attempts.sql before updated binaries. VendorSettlementLedger is a merchandise-only sandbox subledger, not an approved payable or general ledger. One sale entry per vendor order and one negative entry per verified refund. No UPDATE/DELETE operation is exposed. Admin-only sync is gated by SandboxRefundEnabled, SettlementPreviewEnabled (both false unless explicitly configured) and existing development sandbox checkout/finance flags. Vendor owner sees only their own existing finance register. Posting requires a paid order with exact stored gateway metadata, recorded delivery, historical commission snapshot, no pending/approved returns, and matched verified refund evidence for all physically received items. Later returns hold the preview; after verification a subsequent sync appends reversal entries without altering the original sale. The test-only policy reverses original commission proportionately to verified refund amount with cumulative three-decimal rounding; it is not an agreed commercial policy. Ledger net excludes delivery fees, VAT, provider charges, disputes, return-window reserves and payouts. The database transaction serializes with the parent order and refund records, and unique indexes reject duplicate sale/refund source entries. No live gateway refund or payout, no real account settlement, no changes to original Payments or commission snapshot. A migration and actual browser verification remain necessary. A manual settlement approval, vendor agreement on reversal, reconciliation to provider balances, payout execution/idempotency and production controls are future release gates.
